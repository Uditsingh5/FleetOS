<USER_REQUEST>
You are a senior full-stack engineer and system architect.

Build a production-quality MERN-stack web application called:

WATERFLEET OS
"Water Scarcity Response, Fleet Tracking & Emergency Distribution Platform"

The application is designed for cities/municipalities facing water shortages.

The platform coordinates:
1. Citizens who report water shortages
2. Administrators/operators who validate and assign requests
3. Drivers who operate water tankers/vehicles
4. Vehicles/tankers that deliver water
5. Real-time fleet tracking
6. Task assignment and lifecycle management
7. Emergency prioritization
8. Delivery verification
9. Operational analytics

The system should NOT look like a generic CRUD dashboard.

It should feel like a real operational command center for managing water scarcity incidents.

==================================================
2. CORE PRODUCT IDEA
==================================================

WaterFleetOS solves this problem:

During water scarcity, authorities receive multiple requests from different neighborhoods.

The operations team needs to know:

- Where is water needed?
- How severe is the shortage?
- How many people are affected?
- Which requests are emergency cases?
- Which tankers are available?
- Where are the tankers currently located?
- Which driver is available?
- Which tanker has enough capacity?
- Which vehicle should be assigned?
- What route should it take?
- Has the tanker reached the destination?
- Has water been delivered?
- How long did the response take?
- Which areas repeatedly experience shortages?

The application should provide a unified operational system for this.

8. TASK ASSIGNMENT ENGINE
==================================================

Implement an assignment recommendation algorithm.

When an admin opens a request:

Find candidate vehicles that:

1. Are AVAILABLE
2. Are ACTIVE
3. Have enough water
4. Have sufficient capacity
5. Have an available driver
6. Are geographically close

Calculate a simple score.

Example:

score =
    distanceScore
    + capacityScore
    + availabilityScore
    + waterLevelScore

Prefer:

- closest vehicle
- sufficient water
- available driver
- appropriate capacity

Return the top 3 recommended vehicles.

Recommended Vehicles

9. ROUTE / ETA
==================================================

For MVP:

Use a basic distance calculation such as Haversine formula.

Calculate:

distance between vehicle and destination

Then:

ETA = distance / estimated average speed

Do NOT implement complex routing algorithms.

Structure the service so a real routing provider can be integrated later.

Create:

route.service.js

with functions such as:

calculateDistance()
estimateETA()
generateRoute()

Later this can be replaced with:

OSRM
Google Maps
Mapbox

without changing the assignment architecture.

==================================================

29. CONCURRENCY SAFETY
==================================================

Task assignment must prevent two admins from assigning the same vehicle simultaneously.

Use atomic MongoDB updates where possible.

Example concept:

Find vehicle where:

status = AVAILABLE

Then atomically update:

status = ASSIGNED
driverId = ...

If update fails:

vehicle was already assigned.

Return conflict.

Do not rely only on:

find()
then save()

for critical assignment operations.

Use MongoDB transactions when multiple related documents must change atomically.

For example:

Vehicle assignment:

Vehicle
+
Driver
+
Task
+
Request

should be updated consistently.

48. BATTERY-EFFICIENT GPS TRACKING
==================================================

IMPORTANT:

The driver mobile application must NOT continuously keep GPS/location
tracking active.

The system is designed for water tanker drivers who may spend many hours
operating vehicles.

Continuous GPS tracking would unnecessarily consume battery and mobile
data.

Implement a battery-conscious, duty-cycle based location tracking system.

--------------------------------------------------
TRACKING STATES
--------------------------------------------------

The driver app has different tracking modes based on task state.

1. OFFLINE / NO ACTIVE TASK

GPS:
OFF

Do not actively request location.

The backend retains only the driver's last known location.

--------------------------------------------------

2. TASK ASSIGNED BUT NOT STARTED

GPS:
LOW FREQUENCY

Suggested interval:

60–120 seconds

Purpose:

- operational visibility
- approximate driver location
- assignment monitoring

Do not continuously track.

--------------------------------------------------

3. ACTIVE JOURNEY / EN_ROUTE

GPS:
ACTIVE BUT INTERMITTENT

Suggested target:

10–15 seconds

OR

when the vehicle moves approximately 50–100 meters.

Whichever condition occurs first can trigger a location update.

The app should not keep the GPS hardware continuously active
between required updates.

Example:

T0:
Acquire location

T0 + 10–15 sec:
Acquire location

Send update

Sleep

T0 + 20–30 sec:
Acquire again

Evaluate movement

Send only if necessary

This reduces unnecessary GPS and network usage.

--------------------------------------------------

4. APPROACHING DESTINATION

When the vehicle is close to the destination, increase tracking frequency.

Suggested:

5–10 seconds

OR

movement threshold of approximately 25–50 meters.

Reason:

At this stage accurate ETA and arrival detection are more important.

--------------------------------------------------

5. ARRIVED

When the driver marks ARRIVED:

Reduce tracking frequency significantly.

Suggested:

30–60 seconds

or disable active tracking if the vehicle is stationary.

--------------------------------------------------

6. DELIVERING

The vehicle is normally stationary.

GPS:

LOW FREQUENCY / EVENT BASED

Do not continuously collect GPS.

--------------------------------------------------

7. TASK COMPLETED

Immediately stop active GPS tracking.

GPS:

OFF

The driver application returns to normal battery-saving mode.

49. LOCATION COLLECTION ALGORITHM
==================================================

Do not implement:

setInterval(() => {
    navigator.geolocation.getCurrentPosition(...)
}, 1000)

This is inefficient and must NOT be used.

Instead create a dedicated location tracking service.

Example:

locationTrackingService.js

Responsibilities:

startTracking()
stopTracking()
updateTrackingMode()
requestLocation()
shouldSendLocation()
calculateMovement()
getTrackingInterval()

The service should determine:

- current task status
- current tracking mode
- battery state if available
- distance travelled
- time since previous update
- whether the driver is moving
- whether the destination is nearby

before requesting/transmitting another location.

52. NETWORK-AWARE LOCATION TRANSMISSION
==================================================

Do not send unnecessary network requests.

arrival
delivery completion
incident reports

When connection returns:

sync queued critical events.

mark location as low-confidence
